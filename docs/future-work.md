## 1. 複合質問のクエリ分解（query decomposition）

### 背景

`docs/requirements.md` 11-24 に記録された**唯一の実害あるハルシネーション事例**の根本原因。

- 質問「つみたて投資枠と成長投資枠、それぞれの年間投資枠と対象年齢を教えてください」（4事実を要求）に対し、
  **「成長投資枠の年間投資枠は1,200万円」**と回答した。
  1,200万円は**生涯**の非課税保有限度額であり、**年間**投資枠240万円とは別概念。
- 数値も出典URLも引用番号 `[n]` も本物だったため、**既存の防御を全て通過した**。
- 原因は、複数の事実を含む質問が**1つのベクトルに平均化**され、必要なチャンクが揃わなかったこと。
  チャンク側で解決した「1断片1事実」の問題が、**質問側で裏返しに現れた**もの。

### 現在の対策（実施済み・対症療法）

- `topK` を 5 → 15 に拡大（必要なチャンクが揃う確率を上げる）
- システムプロンプト規則8を追加（「資料に無い項目は記載がありませんと明示。他項目の数値で埋めるな」）

**いずれも症状の緩和であり、平均化という原因そのものは残っている。**
項目数がさらに多い質問では再発しうる。

### やること

質問を個別の問いに分割し、**それぞれ独立にベクトル検索する。**

```
質問「つみたてと成長、それぞれの年間投資枠と対象年齢は？」
   ↓ 分割
  Q1 つみたて投資枠の年間投資枠は？
  Q2 成長投資枠の年間投資枠は？
  Q3 つみたて投資枠の対象年齢は？
  Q4 成長投資枠の対象年齢は？
   ↓ それぞれ独立に検索（各 topK は小さくてよい）
  Q1 → 最高 0.81 → 資料あり
  Q2 → 最高 0.79 → 資料あり
  Q3 → 最高 0.74 → 資料あり
  Q4 → 最高 0.41 → 【資料なしと機械的に確定】
   ↓ 重複を除いて統合し、参考資料としてLLMへ
```

### 期待される効果

1. **各サブ質問の埋め込みが鋭くなる。** 平均化が起きない。
2. **「答えられない項目」を、AIに聞く前にシステム側が確定できる。**
   現在は規則8でAIに判断させているが、これを閾値による機械判定に移せる。
   → 11-24の「他項目の数値で穴を埋める」事故が**構造的に起きなくなる**。
3. サブ質問ごとに閾値を適用できるため、部分回答の根拠が明確になる。

### 分割方法：2案

#### 案A：LLMに分割させる（**利用者の希望はこちら**）

- 日本語の複雑な文（「AとBの、CとD」型）にも対応できる。**11-24の事例を実際に解決できるのはこちらのみ。**
- 利用者は 2026-09-05 時点で「AIが判断してもよい」との意向。

**⚠️ ただし、必ず下記の縛りを付けること。**

本設計の基本方針は「**安全判定の手前にAIの判断を入れない**」である。
分割にLLMを使うことはこの方針への例外となるため、以下を必須とする。

| # | 必須の制約 |
|---|---|
| A-1 | **分割専用のプロンプトを使う。**「質問を分けるだけ。答えない。情報を足さない。元の文言を保つ」 |
| A-2 | **出力を機械検査する。**分割後の各サブ質問に含まれる名詞・数値が、**元の質問に存在するか**を照合する。元に無い語（特に数値）が混入していたら、**その分割結果を破棄し、元の質問1本で検索する**（現行方式にフォールバック） |
| A-3 | **分割は「成功すれば得」の位置づけにする。**失敗・タイムアウト時は必ず現行方式に戻す。分割に依存しない |
| A-4 | 分割数に上限を設ける（例：最大5）。上限超過時はフォールバック |
| A-5 | 分割用のLLM呼び出しは**軽量モデル**を使い、`max_tokens` を小さく抑える（無料枠への影響を最小化） |

> **A-2 が最重要。** これが無いと、AIが「成長投資枠の枠は？」を
> 「成長投資枠の年間投資枠240万円について」のように**答えを混入させた形に書き換える**危険がある。
> `docs/requirements.md` 11-9 で修正した「20.315%」と同じ種類の混入が、
> **検索の入口で起きると、以降の全ての防御が無意味になる。**

#### 案B：機械的に分割する（AIを使わない）

- 文の切れ目（`。` `？` `?`）と明示的な接続語（「また」「あと」「それと」）でのみ分割。
- **`と` や `、` では絶対に分割しない**（「つみたて投資枠と成長投資枠」が壊れる）。
- 費用ゼロ・遅延ゼロ・決定的（同じ入力に同じ結果）。
- ただし **11-24の事例（1文に4事実）は分割できない。**

#### 推奨

**案Aを本命とし、案Bを併用する。**
まず案Bで安全に分割できるものを分割し、それで分かれなかった場合に案Aを試す。
案Aが A-2 の検査に落ちたら、現行方式（分割なし・topK 15）にフォールバックする。
**3段構えにすることで、AIの判断に依存する範囲を最小化できる。**

### 再ランキングとの組み合わせ（2026-09-05 追記）

**クエリ分解と再ランキング（項目4）は排他ではない。業界標準では両方を含む構成が使われている**
（RAG-Fusion：BM25＋ベクトル × LLMによる質問書き換え → RRFで統合 → クロスエンコーダで再ランキング）。

効く場所が違うため競合しない。

```
質問
 ├─【① クエリ分解】     ← 検索の「前」。質問を鋭くする
 ├─【② 各サブ質問で検索】
 ├─【③ 統合】
 ├─【④ 再ランキング】   ← 検索の「後」。取ってきた中から正確に選ぶ
 └─【⑤ 回答生成】
```

**むしろ、分解は再ランキングの必要性を高める。**
分解前は「1質問 → 15件」で済んでいたものが、分解後は「4サブ質問 × 各20件 = 最大80件」になり、
**候補が多すぎるという新しい問題が生まれる。**その受け皿が再ランキングである。

#### 【最重要】統合の方法を間違えると、分解の意味が消える

| 方法 | 内容 | 評価 |
|---|---|---|
| **やり方A（NG）** | 全候補をまとめ、**元の質問**に対して再ランキングし上位N件を採る | **採用しない** |
| **やり方B（採用）** | **サブ質問ごとに**再ランキングし、**各サブ質問に枠を割り当てて**確保する | **こちら** |

**やり方Aが駄目な理由**：元の質問は話題の濃淡があるため、濃い話題の証拠ばかりが上位を占める。

```
元の質問「…それぞれの年間投資枠と対象年齢は？」
 → 再ランキング上位5件が全て「年間投資枠」関連で埋まる
 → 「対象年齢」の証拠（Q3・Q4の答え）が1件も残らない
 → 分解して確保したはずの証拠を、統合の段階で捨てている
```

**やり方Bの形**：

```
Q1の候補20件 → Q1に対して再ランキング → 上位2件を確保
Q2の候補20件 → Q2に対して再ランキング → 上位2件を確保
Q3の候補20件 → Q3に対して再ランキング → 上位2件を確保
Q4の候補20件 → Q4に対して再ランキング → 上位2件を確保
                                          ↓ 計8件をLLMへ
```

- **各サブ質問に必ず枠を割り当てる**ことで、分解の目的（各項目の証拠を漏らさない）が最後まで守られる。
- サブ質問ごとの最高スコアが閾値未満なら、**その項目だけを「資料に記載なし」と機械的に確定できる**
  （項目1の「期待される効果2」がここで実現する）。

#### RRF（Reciprocal Rank Fusion）について

複数クエリの結果を統合する業界標準の手法。点数ではなく**順位のみ**を使う。

```
ある資料のスコア = Σ ( 1 ÷ (k + その質問での順位) )    ※ k = 60 が業界の慣例値
```

- 目的は「点数が出やすい質問の結果ばかりが上位を占める」問題（スコアの非互換性）の回避。
- **ただし本件では、RRFよりやり方Bのほうが適している。**
  RRFは「**同じ質問の言い換え**を複数投げて総合的に良いものを選ぶ」用途に向く。
  本件のサブ質問は**それぞれ別のことを聞いている**ため、統合して1つの順位にするより、
  **各サブ質問の枠を独立に守る**ほうが目的に合う。
- ハイブリッド検索（項目5）を導入する場合は、BM25とベクトルの統合にRRFを使うこと。

#### 段階的な導入順序（推奨）

```
① 工程8で、現在の対策（topK 15＋規則8）の実力を測る
      ↓ 不十分なら
② クエリ分解だけを入れる（再ランキングなし、各サブ質問 topK 5 程度）
      ↓ 候補が多すぎて参考資料の枠に収まらないなら
③ 再ランキング（項目4）をやり方Bで足す
```

**②の時点で解決する可能性が高い。**サブ質問1つに絞れば検索が鋭くなるため、
各 topK が小さくても正解チャンクが入るはず。候補が増えすぎないなら再ランキングは不要。

#### コスト概算（予算方針を踏まえて）

| 処理 | 呼び出し | 1問あたり概算 |
|---|---|---|
| 現行 | 埋め込み1回＋検索1回＋生成1回 | 約 $0.00028 |
| ＋分解 | LLM 1回（軽量モデル・入出力とも小）＋埋め込みと検索がサブ質問の数だけ | **＋$0.00005 前後（約+18%）** |
| ＋再ランキング | サブ質問数 × 候補数 のペア評価 | **要確認**（`@cf/baai/bge-reranker-base` の単価を公式ページで確認すること） |

- **分解だけなら、1日390問 → 約330問。無料枠の範囲でも十分収まる。**
- 再ランキングの単価は未確認。導入判断の前に 1-7 と同じ手順で公式ページを確認し、確認日を残すこと。
- **再ランキングを入れると閾値の意味が変わる**（コサイン類似度ではなく再ランカーのスコアで判定することになる）。
  現在の `0.67` / `0.62` は**測り直しになる**。項目2（評価の自動化）を先に作っておくと、この測り直しが安価になる。

### 着手条件

**工程8（評価）で複合質問8問以上を測定し、現在の対策（topK 15＋規則8）の実効性を確認してから。**

- 8問とも正しく答えられるなら、本項目は不要な可能性がある。
- 落ちる場合、**どういう落ち方をするか**（必要チャンクが揃わないのか／揃っても取り違えるのか）が

## 2. RAG評価パイプラインの自動化

### 背景

工程4.5〜4.12で、以下を**すべて人手で6サイクル**回した。

```
測る → 取り違えを発見 → 原因を特定 → 直す → 凍結 → また測る
```

- 作成した検証設問は P1〜P54・N1〜N7・R1〜R20 の計81問（＋複合質問セット）。
- 新しいマニュアルやナレッジを追加するたびに、**同じ作業が必要になる。**
- 手作業では回数が限られ、実際に3回「検証セットの汚染事故」が起きた（11-16(4)・11-19(2)）。

### やること

検証セットを**固定資産**として持ち、チャンクを更新するたびに**自動で回帰テスト**する。

#### 2-1. 検証セットのファイル化

```
docs/eval/
  positive.jsonl   … 答えられるべき質問（期待チャンクID付き）
  negative.jsonl   … 拒否すべき質問（期待：scope チャンク or 閾値未満）
  compound.jsonl   … 複合質問（期待：項目ごとの正誤）
```

各行の形（案）：

```json
{"id":"P09","question":"つみたてのほうは1年でいくらまで買えますか","expect_chunk":"fsa-nisa-0008","type":"B"}
{"id":"N01","question":"iDeCoの掛金上限はいくらですか","expect":"reject","expect_scope":"scope-0005","type":"D"}
```

#### 2-2. 自動測定スクリプト

- `data/chunks.jsonl` を投入したあと、検証セット全件を `/api/chat`（または検索のみのエンドポイント）に流す。
- 記録する項目：**最上位チャンクID／最上位スコア／閾値判定の結果／期待との一致**。
- 出力：`docs/eval/results-YYYYMMDD-HHMM.md`（人が読める表）＋ 機械可読なJSON。

#### 2-3. 回帰判定

- 前回の結果と比較し、**新たに落ちるようになった質問（デグレード）を検出**して警告する。
- 通過率だけでなく、**個々の質問の合否の変化**を見ること。

#### 2-4. 閾値の自動再計算

- 拒否側の最高スコアと正解側の最低スコアを算出し、11-13 の判定基準を適用して推奨閾値を出す。
- **自動適用はしない。**人が確認して `wrangler.jsonc` の `vars` を更新する。

### 設計上の重要な注意

| # | 注意 |
|---|---|
| 2-a | **検証セットは実装担当が読める場所に置いてはならない**（11-16(4) の汚染事故の再発防止）。想定質問（`assumed_questions`）を書く担当が検証設問を見ていると、テストの答えを丸暗記させるのと同じになり、測定が無意味になる |
| 2-b | 自動化するなら、**検証セットは十分な数を用意し、一部を「開示しない予備」として残す**運用にする |
| 2-c | **サイクルをまたいだ通過率の単純比較は無効**（11-22(4)）。セットが違えば難易度も違う。比較できるのは同一セット内の相対関係のみ。自動化するなら**同一セットで比較する**こと |
| 2-d | 測定は**非破壊**で行う。測定中にチャンクを変更しない（凍結コミットのハッシュを記録する運用を継続） |

### 着手条件

工程8で検証セットの型（類型A〜I、判定基準）が固まってから。
いま自動化しても、測る対象の定義が動くと作り直しになる。

## 3. 本番ログを使った継続的評価

### 背景

いまの検証設問は、すべて**設計担当が想像で書いたもの**である。

- 実際の利用者がどう聞くかは、まだ誰も知らない。
- 11-22(5) で「合計を問う質問が弱い」等の恒常的弱点が見つかったが、
  これは**たまたまその聞き方を思いついた**から見つかったにすぎない。
- 利用者の実際の質問を集めれば、**想像で作った検証セットよりはるかに良い材料**になる。

### やること

```
実際の質問 → 引いたチャンク → 返した回答  を記録
        ↓
   後から人が正誤を付ける
        ↓
   誤りのあったものを検証セットに追加
        ↓
   チャンク・想定質問を修正 → 2の自動テストで回帰確認
```

#### 記録する項目（案）

| 項目 | 用途 |
|---|---|
| 質問文 | 検証セットの素材 |
| 最上位チャンクID・スコア | 取り違えの分析 |
| 採用したチャンクID一覧 | 再現率の分析（必要なものが揃っていたか） |
| 閾値判定の結果 | 取りこぼし／誤通過の分析 |
| 返した回答 | 誤答の分析 |
| `no_answer` / `error` の別 | 「分かりません」率の監視 |
| タイムスタンプ | 傾向の推移 |

#### 人によるラベル付け

- `正しい` / `取り違え` / `取りこぼし（答えられるはずが分かりませんになった）` / `誤答（ハルシネーション）`
- **`取りこぼし` と `誤答` が改善の材料になる。**
- ラベル付きの質問を、項目2の検証セットに追加していく。

### ⚠️ 着手前に必ず決めること

#### 3-a. 現在の設計との衝突

`docs/requirements.md` の前提に **「Workers は状態を保持しない」** がある。
ログを残すには保存先（KV / D1 / R2 など）が必要で、**アーキテクチャの変更を伴う。**
無料枠の範囲・保存期間・容量を再調査すること（1-7 と同じ手順で、公式ドキュメントを確認し確認日を残す）。

#### 3-b. 個人情報の扱い（**最重要**）

**質問文には利用者の個人的な情報が入りうる。**

```
「私は45歳で年収600万円ですが、NISAはいくらまで…」
「〇〇銀行で口座を作ったのですが…」
```

これを無検討に保存・保持すると、学習用プロジェクトであっても問題になる。着手前に以下を決めること。

| # | 決めること |
|---|---|
| 3-b-1 | **そもそも質問文を保存するか。**スコアと判定結果だけなら個人情報を持たずに済む（ただし検証セットの素材にはならない） |
| 3-b-2 | 保存するなら**保持期間**（例：30日で自動削除） |
| 3-b-3 | 年齢・金額・金融機関名などを**保存前にマスクするか** |
| 3-b-4 | 画面に「入力内容が記録される」旨を明示するか（学習用デモであっても、記録するなら明示すべき） |
| 3-b-5 | ログの保存先が公開リポジトリに入らないこと（`.gitignore` の対象にする） |

> 本プロジェクトは学習目的・実運用しない前提だが、
> **「学習用だから記録してよい」とはならない。**着手時に上記を明文化してから実装すること。

### 着手条件

項目1・2の後。かつ 3-b（個人情報の扱い）を利用者が決めてから。

## 4. 再ランキング（reranking）

### これは何か

**質問と資料を「一緒に読ませて」、その資料が質問に答えているかを直接採点する**モデル。

現在の検索（埋め込み）との違い：

| | 仕組み | 精度 | 速度 |
|---|---|---|---|
| **埋め込み（現行）** | 資料と質問を**別々に**座標化し、座標の距離を測る。資料の座標は事前計算して保存済み | 粗い | 速い。件数が増えても平気 |
| **再ランキング** | 質問と資料を**同時に**入力し、関連度スコアを直接出力する。事前計算できない | 高い | 遅い。件数に比例して増える |

公式ドキュメントの説明：
> reranker は質問と文書を入力として、埋め込みではなく**類似度を直接出力**する。
> スコアはシグモイド関数で [0,1] の float にマップされる。

**別々に作った座標では「年間」と「生涯」の区別がつきにくいが、
一緒に読めば文脈の食い違いに気づける。**（11-24 の 1,200万円 / 240万円 の取り違えがこの型）

### Cloudflareで使えるか → **使える**

| | |
|---|---|
| モデルID | **`@cf/baai/bge-reranker-base`**（BAAI製。埋め込みの `bge-m3` と同じ開発元） |
| 状態 | 提供中（2026-09-05 確認）。タスク分類は "Text Classification" |
| 単価 | **未確認。導入判断の前に公式モデルページで確認すること** |
| 公式の注意 | 「リクエストにステップが1つ増えるため、**レイテンシが増加する可能性**がある」 |

### ⚠️ 単体では 11-24 の不具合を直せない

**最重要の限界。**

> 再ランキングは**再現率を改善しない。すでに取得済みの集合の中でしか働かない。**

11-24 の事故では、正解チャンク（`fsa-nisa-0014`＝240万円）が **topK=5 に入っていなかった**。
取ってこなかったものは、並べ替えでは戻ってこない。

```
再ランキング  = 持ってきた中から良いものを選ぶ処理
              ≠ 持ってこなかったものを取りに行く処理
```

**必ず「候補を多く取る（topK拡大 or クエリ分解）」とセットで使うこと。**

```
【いま】       15件取る → 閾値で絞る → 全部LLMへ
【標準構成】   50件取る → 再ランキングで上位5件 → LLMへ
```

50件取っても再ランキングで5件に絞れば、**LLMに渡す量は増えない。
取りこぼしを減らしながら、同時にノイズも減らせる。**

### やること

1. `@cf/baai/bge-reranker-base` の単価とレイテンシを公式ページで確認（確認日を残す）。
2. topK を拡大（15 → 30〜50）し、再ランキングで上位N件に絞る構成に変更。
3. **項目1（クエリ分解）と併用する場合は、必ず「やり方B」**（サブ質問ごとに枠を確保）で実装する。項目1の該当節を参照。
4. **閾値を測り直す。** 判定に使うスコアがコサイン類似度から再ランカーのスコアに変わるため、
   `0.67` / `0.62` はそのままでは使えない。11-13 と同じ手順で両側を測定し直すこと。

### 着手条件

**項目1（クエリ分解）を入れて、候補が多すぎて参考資料の枠（3,000字）に収まらなくなってから。**
分解だけで解決するなら不要。

## 5. ハイブリッド検索（BM25 ＋ ベクトル）

### 背景

> **2026年の本番環境の標準。** キーワード検索（BM25）とベクトル検索を組み合わせる。
> **純粋なベクトル検索は完全一致に弱く**、純粋なキーワード検索は意味の類似を取り逃す。

**本プロジェクトで記録された恒常的弱点が、まさにこれに該当する**（`docs/requirements.md` 11-22(5)）。

| 質問 | スコア |
|---|---|
| 「両方あわせると1年でいくらになりますか」（P11） | 0.5376 |
| 「2つの枠を両方使うと年間の合計はどうなりますか」（P48） | 0.5331 |

「**360万円**」「**年間投資枠**」といった**正確な語**は、キーワード検索なら確実に当たる。
ベクトル検索は「だいたいの意味」で探すため、ピンポイントの語や数値が苦手。

### ⚠️ 技術的な障壁

**Cloudflare Vectorize はベクトル検索専用で、BM25（キーワード検索）の機能を持たない。**

導入するには別の仕組みが必要になる。着手前に以下を調査すること。

| 選択肢 | 検討事項 |
|---|---|
| D1（SQLite）の全文検索（FTS5）を併用 | Workers から使える。無料枠・日本語の分かち書きの扱いを要確認 |
| 46件程度なら Worker 内で単純な語一致スコアを計算 | 件数が少ないうちは自前実装でも足りる可能性 |
| 外部の検索サービス | APIキーが必要になり、当初方針（キー不要）から外れる |

**件数が46件と少ないうちは、3つ目の選択肢は不要。2つ目で十分な可能性が高い。**

### 統合方法

ベクトル検索とキーワード検索は**スコアの尺度が違う**ため、単純に足せない。
業界標準は **RRF**（項目1の該当節を参照）。順位のみを使うため尺度の違いを回避できる。

### 着手条件

項目1・2の後。かつ、工程8で「正確な語を含む質問の取りこぼし」が実際に問題として確認されてから。

## 6. 拒否時の言い換え提案（smart query suggestions）

### 背景

現在、閾値 `0.67` は**答えられるはずの質問も落としている**（11-22(3)）。

| 質問 | スコア |
|---|---|
| 2つの枠を両方使うと年間の合計はどうなりますか | 0.5331 |
| 大学生でもNISAは使えますか | 0.6249 |
| 普通の口座だと利益から何割くらい引かれますか | 0.6322 |
| つみたてと成長で会社を分けることは可能ですか | 0.6599 |

閾値を下げると拒否側（最高 0.6632）が通り始めるため、**閾値では解決できない。**

業界でも同じ問題が認識されている：
> 厳格なガードレールは、**範囲外の語を含むだけで、正当な意図の質問まで
> 行き止まりの拒否にしてしまう**ことが多い。

### やること

拒否したときに、**答えられる形の質問例を提示する。**

```
【いま】
  「提供された資料の範囲では分かりません。金融庁のNISA特設サイトをご確認ください。」

【この案】
  「提供された資料の範囲では分かりません。
    こうした聞き方であればお答えできる場合があります：
      ・つみたて投資枠の年間投資枠は？
      ・成長投資枠の年間投資枠は？」
```

### 実現方法（LLMを使わずにできる）

- チャンクの `assumed_questions`（想定質問）は**すでに全チャンクに付いている**。
- 拒否した質問に対して、**閾値未満でも最も近かったチャンクの `assumed_questions` を提示する**だけでよい。
- LLM呼び出しは不要。**追加コストほぼゼロ。**

### 注意

| # | 注意 |
|---|---|
| 6-a | **提案する質問文に、答え・数値を含めないこと。**`assumed_questions` は元々この制約で書かれているため、そのまま使える |
| 6-b | 対象範囲外チャンク（`scope-*`）が最上位だった場合は提案しない。その場合は範囲外の案内文を返すのが正しい |
| 6-c | 提案は「お答えできる**場合があります**」という表現にする。必ず答えられると約束しない |

### 着手条件

**いつでも可能。**追加コストがほぼ無く、既存のデータだけで実現できるため、
項目1〜5の中では最も安価に取りこぼしを緩和できる。

## 補足：各項目の関係と、効く場所

```
質問
 │
 ├─【1 クエリ分解】      検索の「前」  … 質問を鋭くする（本命）
 │
 ├─【5 ハイブリッド検索】検索「そのもの」… 正確な語の取りこぼしを拾う
 │
 ├─【4 再ランキング】    検索の「後」  … 多い候補から正確に選ぶ
 │
 ├─【6 言い換え提案】    拒否した「後」… 取りこぼしを利用者側で救う
 │
 └─ 回答生成

  【2 評価の自動化】 … 上記すべての効果を測る土台
  【3 本番ログ活用】 … 何を直すべきかを実データから見つける
```

**1・4・5 は競合しない。それぞれ別の場所に効く。**（項目1の「再ランキングとの組み合わせ」を参照）

### 推奨する順序

```
① 工程8（評価）で現状の実力を測る          ← 現行スコープ
② 6 言い換え提案（最も安価。既存データだけで可）
③ 1 クエリ分解（本命。11-24の恒久対策）
④ 2 評価の自動化（③の効果測定と、以降の回帰テストの土台）
⑤ 4 再ランキング / 5 ハイブリッド検索（③で足りなければ）
⑥ 3 本番ログの活用（個人情報の扱いを決めてから）
```

- **2 を先に作れば、以降の効果測定が安価になる。**ただし工程8で測定対象の型が固まってからでないと作り直しになる。
- **4・5 を入れると閾値の測り直しが発生する。**2 が先にあると、この測り直しが自動化される。
- 最終的な順序は利用者が決めること。
