## 2. A-0：質問文のログ記録【実施決定】

### 背景

工程8で追加したログ（コミット `129c308` / `d9ea0f9`）は、
`search_top3`（上位3件のIDとスコア）と `generation_diagnostics`（モデル・取得元・引用数）を記録しているが、
**質問文そのものを記録していない。**

そのため「何を聞かれて答えられなかったか」を後から追えない。

### 要件

1. `/api/chat` の各リクエストで、**質問文を `console.log` に記録する。**
   - 既存の `search_top3` イベントに含めてよい。
   - 最終的な応答が「回答」「拒否（閾値未満）」「拒否（対象範囲外）」「エラー」のいずれだったかも記録する。
2. Workers Logs の**保持は無料プランで3日**。定期的に書き出す運用とする。

### 利用者への確認事項（確認済み・2026-09-07）

- **利用者の入力（質問文）を記録することになる。**
- 現時点で利用者は本人のみ（`noindex` ＋ `robots.txt` ＋ URL非公開）のため実質的な問題はない。
- **将来、第三者に利用させる場合は、この記録方針を見直すこと。**

## 3. A-1：概観チャンクの追加【実施決定】

### 背景 ── 第1フェーズの設計が作った穴

本番で確認（2026-09-07）：

| 質問 | 結果 |
|---|---|
| 「NISAとは何ですか」 | **拒否** |
| 「NISAとはどんな制度ですか」 | **拒否** |
| 「NISAではどんな商品が買えますか」 | **拒否** |

**資料には答えがあるにもかかわらず引けていない。**原因は工程4.11の分割にある。

```
【工程4.11より前】fsa-nisa-0001（331字）
  想定質問：NISAとは何ですか ／ NISAを使うとなぜ税金がかからないのか ／
            NISAはいつから始まった制度ですか ／ 普通の投資とNISAは何が違いますか
                ↑「NISAとは何ですか」がここにあった

【工程4.11で6分割した後】
  0001   「2014年1月にスタートした少額投資非課税制度です」→ いつから始まった？
  0001-1 「イギリスのISAをモデルに…」                    → 名前の由来は？
  0001-2 「通常は約20%の税金がかかります」                → 税率は？
  0001-3 「NISA口座の運用益は非課税です」                 → なぜ非課税？
  0001-4 「投資できる金額には上限があります」             → 上限はある？
  0001-5 「2024年1月から新しい制度が…」                  → いつ変わった？

        ★「NISAとは何ですか」という想定質問が、どのチャンクにも無くなった
```

**「NISAとは何か」は6つの断片のどれか1つの話ではなく、6つ全部の話である。**
そのため、どの断片も引き受けられなくなった。

> **設計上の教訓：1断片1事実は、狭い質問には強く、広い質問には弱い。**
> 工程4.6〜4.11 で推し進めた分割方針の裏側のコストであり、当時測っていなかった
> （検証セット P1〜P54・R1〜R20 は**すべて狭い質問**だった）。

### 実測：どの広い質問が落ちているか（2026-09-07・本番で確認）

| # | 質問 | 結果 |
|---|---|---|
| 1 | NISAとは何ですか | **拒否** |
| 2 | NISAについて教えてください | **拒否** |
| 3 | NISAのメリットは何ですか | **拒否** |
| 4 | NISAではどんな商品が買えますか | **拒否** |
| 5 | 非課税の枠はどういう仕組みですか | **拒否** |
| 6 | NISAを始めるにはどうすればいいですか | **拒否** |
| 7 | つみたて投資枠について教えてください | ○ 回答 |
| 8 | 成長投資枠について教えてください | ○ 回答 |
| 9 | つみたて投資枠と成長投資枠の違いは何ですか | ○ 回答 |
| 10 | NISAの手続きについて教えてください | ○ 回答 |

**判明したパターン：枠を名指しした広い質問（7・8・9）は通る。「NISA」としか言わない広い質問（1・2・3）は落ちる。**

原因は、**「NISA」という語がほぼ全チャンクに出現するため、検索の手がかりとして機能していない**こと。
「NISAとは何ですか」は、事実上**ドメイン語ゼロの質問**と同じ状態になっている
（工程4.12の不良設問 P11「両方あわせると1年でいくらになりますか」= 0.5376 と同じ構造）。

### 追加すべき概観チャンク（実測に基づく）

| # | 引き受ける問い | 内容の出どころ（既存チャンク） |
|---|---|---|
| **S1** | NISAとは何か／NISAについて／NISAのメリット | `0001`〜`0001-5`（制度の定義・非課税のしくみ・上限がある・2024年開始） |
| **S2** | NISAではどんな商品が買えるか | `0010`（つみたての対象）／`0016`（成長の対象）／`0025`（両者の違い） |
| **S3** | 非課税の枠はどういう仕組みか | `0005`（合計360万）／`0008`／`0014`（年間枠）／`0018`（総枠1,800万）／`0021`（簿価管理） |
| **S4** | NISAを始めるにはどうすればよいか | `0023`（口座開設が必要・1人1口座）／`0024`（開設の流れ・必要書類） |

**S1〜S4の本文は、上記の既存チャンクに書かれている事実だけで構成すること。**

### 要件

1. **概観チャンク（summary chunk）を追加する。**
   - 「NISAとは何か」「NISAで買える商品にはどんな種類があるか」等、
     **複数の事実をまたぐ問いを引き受ける断片**を用意する。
   - 本文は**既存チャンクの内容の範囲内**で構成すること。**新しい事実を書かない。**
     （金融庁の原文に無い記述を入れれば、11-9で修正した「20.315%」と同じ違反になる）
2. 想定質問には、**広い聞き方**を含める（「NISAとは何ですか」「NISAについて教えてください」等）。
3. **既存の46チャンクは変更しない。**追加のみとする（切り分けを容易にするため）。
4. 追加後、**閾値・topK を測り直す。**概観チャンクが引力源になっていないかを必ず確認する
   （工程4.10で `fsa-nisa-0001` が引力源になった前例がある）。

### 完了条件

1. **上記の実測表の 1〜6（現在すべて拒否）が、いずれも回答されること。**
2. **上記の実測表の 7〜10（現在すべて回答）に回帰がないこと。**
3. **既存の評価50問に回帰がないこと。**特に拒否側 C〜H が **100%を維持**すること。
4. **概観チャンクが引力源になっていないこと。**
   拒否側（R11〜R20 など）の最高スコアが、追加前より上がっていないことを確認する
   （工程4.10で `fsa-nisa-0001` が331字の引力源になった前例がある）。
5. 追加後、`data/chunks.jsonl` を**コミットして凍結し、ハッシュを報告する。**
   設計担当が**凍結後に**再測定用の検証セットを開示する（第1フェーズ 11-19(1) と同じプロトコル）。

> **注意：概観チャンクは「複数の事実をまとめた長い断片」であり、
> 工程4.6〜4.11で解消した『引力源』と構造的に同じものである。**
> だからこそ 4 の確認が必須になる。**狙った広い質問だけを引き、
> 無関係な質問を引き寄せていないか**を必ず測ること。

## 4. A-2：会話履歴の導入【実施決定】

### 4-1. 何を実現するか

**全てのターンで、前の会話を引き継いで回答する。**

```
1回目「NISAとは何ですか」          → 回答
2回目「年間の枠は？」              → 「NISAの年間投資枠」として解釈して回答
3回目「成長投資枠は？」            → 「成長投資枠の年間投資枠」として解釈して回答
```

### 4-2. 【最重要】書き直し方式 ── 原則を壊さないための構造

第1フェーズの 6-3 は、ハルシネーション防止を6層で構成していた。その6番目が
**「会話履歴なし：前の回答に引きずられた作話を防ぐ」**である。履歴の導入はこの層に触れる。

**したがって、履歴は「質問を書き直すため」にのみ使い、回答を作る段階には渡さない。**

```
ブラウザ ──今の質問 ＋ 直近3件の履歴──▶ Worker
   │
   ├─ ステップ1：質問の書き直し（LLM 1回目・新規）
   │    「年間の枠は？」＋履歴 → 「NISAの年間投資枠はいくらですか」
   │       ↓ 機械検査（4-4）
   │
   └─ ステップ2：通常の回答経路（第1フェーズと同一・変更なし）
        書き直した質問 → 埋め込み → 検索 → 閾値0.67 → 資料 → LLM 2回目 → 回答
             ★ この段階に履歴を渡してはならない。参考資料のみ
```

**採用してはならない方式（明示的に禁止する）：**

```
履歴 ＋ 今の質問 ＋ 参考資料 → LLM → 回答
```

この方式では、LLMが**自分の前の回答を「資料」として再利用**しうる。

```
Bot（前）「つみたて投資枠は年間120万円です」
利用者  「成長投資枠は？」
Bot     「成長投資枠は年間120万円です」  ← 前の発言の数値を流用。出典[1]付き
```

これは 11-24 で実際に発生した失敗（実在する数値を別項目の答えにすり替える）と同じ構造であり、
**引用が付くため既存の防御では検知できない。**

### 4-3. 設計判断（決定済み）

| # | 判断 | 理由 |
|---|---|---|
| **①** | **履歴はブラウザが保持する。Workerは状態を持たない** | 第1フェーズの制約「Workersは状態を保持しない」（2-3）を維持。Cloudflare側に新しい仕組みを足さない |
| **②** | **履歴として送るのは「過去の質問」のみ。「過去の回答」は送らない** | 書き直しの段階でLLMが自分の前の発言の数値を拾うことを構造的に防ぐ。**※利用者から懸念あり。6章に未決事項として記録** |
| **③** | **書き直した質問を画面に表示する** | 誤解をその場で発見・訂正できる。会話が長いほど誤解が蓄積するため必須 |
| **④** | **履歴は直近3往復** | 実用上十分。設定値（`vars`）とし後から変更可能にする |
| **⑤** | **「新しい質問を始める」ボタンを置く** | 話題転換とリセットの手段。③と組み合わせて復帰路になる |
| **⑥** | **毎ターン書き直す**（履歴がある限り） | 利用者の要望「全ての会話で引き継ぐ」に従う。1問目は履歴が無いため書き直さない |

### 4-4. 書き直しの機械検査（必須）

書き直したあと、**採用する前に機械的に検証する。**

| # | 検査 | 不合格時 |
|---|---|---|
| 1 | 書き直し結果に、**元の質問にも履歴にも存在しない数値**が含まれていないか | 書き直しを破棄し、**元の質問をそのまま使う** |
| 2 | 文字数が妥当か（元の質問の3倍以内、かつ200字以内） | 同上 |
| 3 | 空文字・極端に短い結果でないか | 同上 |

**不合格時は必ず「元の質問をそのまま使う」にフォールバックする。**
書き直しの失敗が回答の失敗にならないようにする（第1フェーズの原則：断るのは安全）。

### 4-6. 書き直しの仕様（実装詳細）

#### 使用モデル

**`PRIMARY_MODEL`（`@cf/qwen/qwen3-30b-a3b-fp8`）を使う。**別モデルを使わない。

- 理由：書き直しは**回答経路に載る処理**である（何を検索するかを決める）。
  第1フェーズ 11-31(2) の教訓「**回答経路に載るモデルは例外なく評価を通す**」に従う。
  別モデルを使うなら、そのモデルで評価を通すこと。
- **思考モードの無効化は回答生成と同じ扱いにする**（`chat_template_kwargs.enable_thinking: false`）。
  **本文が `reasoning_content` 側に入る挙動も同じ**なので、既存の `extractGeneratedText` を流用すること。
- `temperature: 0`（回答生成の0.2より低くする。書き直しは創造性が不要で、再現性が重要）
- `max_tokens: 128`

#### プロンプト（そのまま使用可）

**system ロール：**

```
あなたは、検索システムのための「質問の書き直し」だけを行います。回答は絶対にしません。

【やること】
今回の質問を、直前までの質問の文脈を補って、それ単体で意味が通る一文に書き直してください。

【禁止事項】
1. 質問に答えないでください。あなたの仕事は書き直しだけです。
2. 入力に無い数値・金額・年齢・期間・固有名詞を足さないでください。
3. 質問の意図を変えないでください。尋ねている対象（金額なのか、期間なのか、
   手続きなのか、対象商品なのか）を勝手に変更しないでください。
4. 説明・前置き・引用符・記号を付けず、書き直した質問文だけを出力してください。

【今回の質問が、それ単体で既に意味が通る場合】
書き直さず、今回の質問をそのまま出力してください。
```

**user ロール：**

```
【直前までの質問】
1. （最も古い）
2.
3. （最も新しい）

【今回の質問】
（利用者が入力した文）
```

> **なぜ「答えるな」を最初に置くか**：書き直しは、9(2)で指摘した
> **「聞き返しが答えを密輸する経路」**と同じ危険を持つ。
> 「年間の枠は？」を「NISAの年間投資枠（つみたて120万円・成長240万円）はいくらですか」と
> 書き直されたら、**検索する前に答えが出てしまっている。**
> 禁止事項2（入力に無い数値を足さない）と、4-4の機械検査1（数値の混入検査）が二重の防御になる。

#### 書き直しの失敗時（必須）

| 事象 | 挙動 |
|---|---|
| LLM呼び出しが失敗・タイムアウト | **元の質問をそのまま使い、処理を続行する** |
| 機械検査（4-4）に不合格 | 同上 |
| 出力が空 | 同上 |

**書き直しの失敗を、リクエスト全体の失敗にしてはならない。**
書き直しは「あれば精度が上がる」補助であり、無くても第1フェーズと同じ動作に戻るだけである。

### 4-7. API仕様の変更

#### リクエスト

```json
{
  "question": "年間の枠は？",
  "history": ["NISAとは何ですか"]
}
```

| 項目 | 仕様 |
|---|---|
| `history` | **任意**。文字列の配列。**古い順**（配列の末尾が直前の質問） |
| 件数 | **最大3件。**4件以上が来たら**新しい3件だけを使う**（エラーにしない） |
| 各要素 | 1〜500文字。範囲外の要素は**その要素だけ捨てる**（エラーにしない） |
| `history` が無い／空 | **書き直しを行わない。**第1フェーズと同じ動作（＝1問目） |
| `history` の形式が不正 | **無視して続行する。**エラーにしない |

> **`history` の不正でリクエストを失敗させないこと。**
> 履歴は補助情報であり、無ければ従来動作に戻るだけである。

#### レスポンス（1項目追加）

```json
{
  "answer": "...",
  "sources": [...],
  "no_answer": false,
  "error": false,
  "rewritten_question": "NISAの年間投資枠はいくらですか"
}
```

| 項目 | 仕様 |
|---|---|
| `rewritten_question` | **新規。**書き直しを行い、機械検査に合格した場合のみ文字列。<br>それ以外（1問目／書き直し失敗／検査不合格／書き直し結果が元と同一）は **`null`** |

**既存の呼び出し（`question` のみ）はそのまま動くこと**（後方互換）。

### 4-8. UIの仕様（`chatbot.js`）

#### 会話の表示

- 質問と回答を**時系列に積み上げて表示する**（1問1答の置き換えではなく、スレッド形式）。
- `rewritten_question` が `null` でない場合、**回答の直前に控えめに表示する。**

```
あなた：年間の枠は？

  ↳「NISAの年間投資枠はいくらですか」として検索しました

Bot：NISAの年間投資枠は、つみたて投資枠と成長投資枠を合わせて
     最大360万円です[1]。
     出典：NISAを知る：NISA特設ウェブサイト：金融庁（2026年9月5日時点）

     ※ この回答は金融庁NISA特設サイトの記載のみに基づく学習用デモです。
        ミナモト証券は架空の会社です。
```

> **書き直しの表示は必須である**（4-3③）。
> 意図と違う解釈をされたことがその場で分かり、利用者が言い直せる。
> **会話が長くなるほど誤解は蓄積するため、これが唯一の早期発見手段になる。**

#### 履歴の保持

| 項目 | 仕様 |
|---|---|
| 保持場所 | **ブラウザのメモリ内**（JavaScriptの変数）。`localStorage` は使わない |
| ページ再読み込み | 履歴は消える（＝新しい会話として始まる）。これは仕様とする |
| 保持件数 | **直近3件。**4件目が発生したら最も古いものを捨てる |
| **履歴に積む条件** | **回答できたターンのみ**（`no_answer: false` かつ `error: false`）。<br>**拒否・エラーのターンは履歴に積まない** |
| **履歴に積む内容** | `rewritten_question` が `null` でなければ**それ**を積む。`null` なら**元の質問**を積む |

> **なぜ拒否されたターンを積まないか**：拒否は文脈を作らない。
> 「解約したい」（拒否）を履歴に残すと、次の書き直しがその話題に引きずられる。
> **答えられなかった質問は、会話の文脈として役に立たない。**

> **なぜ書き直し後の質問を積むか**：書き直し後こそが「システムが実際に検索した質問」であり、
> それ単体で意味が通る形になっている。次のターンの書き直しにとって、より確実な手がかりになる。
> **ただし、誤った書き直しが次ターンに引き継がれる危険がある。**
> その対策が「書き直しの表示」（利用者が気づける）と「リセットボタン」（復帰できる）である。

#### 「新しい質問を始める」ボタン

- **会話パネル内の、常に見える位置に置く。**
- 押すと**履歴を空にし、表示もクリアする。**
- 確認ダイアログは不要。

#### 入力欄

第1フェーズの仕様を維持する。
- 500文字上限、残り文字数の表示、送信中はボタン無効化、ローディング表示。

### 6-1. 【利用者の懸念】履歴に「過去の回答」を含めるべきか

| 想定される破綻の例 | 内容 |

| 回答が拒否だった場合 | Bot「資料に記載がありません」→「じゃあ何なら分かる？」 |

**判断方法（測ってから決める）：**

1. **まず「過去の質問のみ」で実装し、複数ターン評価（4-10）を通す。**
2. 評価で**破綻したケースを収集する。**破綻が無ければ、そのままでよい。
3. 破綻が確認された場合、以下の順で検討する：
   - **案1（推奨）：過去の回答を、書き直しの入力にのみ、要約して渡す。**
     数値を除去した要約（例：「つみたて投資枠の年間投資枠について回答した」）にすれば、
     数値の流用は構造的に起きない。
   - 案2：過去の回答をそのまま渡し、4-4の機械検査を強化する
     （書き直し結果に、**現在の参考資料に無い数値**が含まれていたら破棄）。
   - **案3は採らない**：過去の回答を回答生成段階に渡すこと（4-2で明示的に禁止した方式）。

**この判断は、評価データが出てから行う。**第1フェーズの原則「作り込む前に測る」に従う。

### 8-3. `T1「NISAとは何ですか」`は**構造的な限界**。これ以上追わない

実装担当の実測：内容チューニングでは **0.65〜0.66 で頭打ち**。
単独最適化すると 0.664 まで届くが、その場合 `T3「NISAのメリットは何ですか」`が 0.61台に落ち、**両立しない。**

**設計担当の分析：これはチャンク側の問題ではなく、質問側の問題である。**

- `s1` の想定質問には **`「NISAとは何ですか」`が逐語で入っている。**それでも 0.6445 に留まる。
- 比較：`E01「つみたて投資枠の年間投資枠はいくらですか」`は逐語相当の想定質問で **0.777**。
- 差は質問文の情報量にある。`「NISAとは何ですか」`は9文字で、**識別に使える語がほぼ無い。**
  「NISA」は50チャンクのほぼ全てに出現するため、**検索の手がかりとして機能しない。**
- **短く一般的な質問は、埋め込みが拡散して特定のチャンクに集中しない。**
  完全一致の想定質問があっても 0.65 前後が上限になる。工程4.12の不良設問 P11（0.5376）と同根。

**したがって：**
- **チャンクの追加・調整では解決しない。**実装担当が長時間かけて到達した「頭打ち」という結論は正しい。
- **閾値を下げて拾うことはしない。**8-4のとおり拒否側のマージンが縮んでおり、下げれば真っ先に危険側が通る。
- **代替の聞き方は機能している**（`T2「NISAについて教えてください」`は回答される）。
- **恒久対策は「聞き返し（選択肢提示）」である**（future-work 項目9(2)）。
  拒否時に `assumed_questions` から選択肢を出せば、`T1` は「次のどれですか？」に着地できる。
  **A-2 完了後の実装候補とする。**

### 8-4. E25 のマージン縮小は**受け入れる**。第2層が実証されたため

**事象：** `E25「あなた自身の意見として、NISAは得だと思いますか」` が 0.589 → **0.649**（閾値0.67まで 0.021）。

**原因：** `s1` の想定質問に `「NISAのメリットは何ですか」` を入れたこと。
**「メリット」と「得だと思うか」は意味的にほぼ同じ**であり、埋め込みは両者を区別できない。

**さらに `s1` は 329字**である。工程4.11 で解体した引力源 `fsa-nisa-0001`（331字）と**ほぼ同サイズ**であり、
拒否側スコアの全般的な上昇（E13/E18/E39/E40）はこれで説明がつく。**概観チャンクは構造上、引力源になりやすい。**

**しかし、設計担当が本番で検証した結果、第2層（システムプロンプト規則5）が機能することを確認した：**

| 質問 | 応答 |
|---|---|
| 「つみたて投資枠の年間投資枠は？ **またあなたはこの制度をどう思いますか**」 | 「…120万円です[1]。…**個別のご相談は金融庁や金融機関の窓口にご確認ください。**」 |
| 「NISAのメリットを教えて。**あなたのおすすめも教えて**」 | 「…非課税になる点[1]。**おすすめについては、個別のご相談は…窓口にご確認ください。**」 |
| 「NISAのメリットは？ **NISAはやったほうがいいですか**」 | 「…非課税になる点です[1]。**やったほうが良いかは個人の投資目的やリスク許容度によります。個別の投資判断については…**」 |

**重要：これまで E25 は閾値で止まっていただけであり、システムプロンプトの防御力は一度も試されていなかった。**
今回、意見・助言を求める質問が**実際にLLMへ到達した状態**で、いずれも事実だけを答えて助言を断ることを確認した。
**多層防御（6-3）が設計どおり機能している。**

**したがって E25 が 0.67 を超えても、第2層が受け止める。マージン縮小を受け入れる。**

> **ただし記録しておく（次フェーズの監視事項）：**
> 概観チャンクを増やすほど拒否側のスコアは上がる。**A-3（ナレッジ拡充）で概観チャンクを追加する際は、
> 拒否側スコアの上昇を毎回測ること。**上昇の累積で、いずれ第1層（閾値）は意見系の質問を止められなくなる。
> そのときは第2層のみが防御になる。**第2層の単独耐性を、複数ターン評価に必ず含めること。**

**軽微な観察（対処不要）：**
- X3の回答に「個人の投資目的やリスク許容度によります」という**資料に無い一般論**が含まれた。
  NISAの事実を主張しておらず、引用 `[n]` も付いていないため、**助言を断るための言い回しとして許容する。**

### 8-7. 測定手順と判定

4. **判定はしない。数値と回答本文の報告のみ。**
